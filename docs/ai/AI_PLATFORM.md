# AI 平台架构设计

> 版本：Draft 1
>
> 目标：把 legado 的 AI 能力从“聊天功能”升级成“可执行任务的平台能力”。
>
> 当前项目已经有 `runtime / tool / bridge / skill / model / log / ui` 七个基础分区，本文件是在这个基础上补齐完整的 AI 平台架构。

---

## 1. 平台目标

AI 平台不是一个单独页面，而是一套贯穿阅读器全局的能力层。它的目标是：

- 让 AI 能理解用户意图
- 让 AI 能调用真实工具
- 让 AI 能在受控条件下修改数据
- 让 AI 的执行过程可追踪、可回放、可审计
- 让 AI 不破坏原有阅读体验

AI 在这个项目里的定位不是“替代 UI”，而是“增强 UI 与业务执行能力”。

---

## 2. 平台边界

### 2.1 AI 可以做什么

- 搜书
- 读章节
- 总结内容
- 分析人物、主题、剧情
- 诊断书源
- 生成修复建议
- 查询设置
- 操作书架
- 执行受控写操作
- 读取运行日志

### 2.2 AI 不能做什么

- 直接绕过确认机制写入敏感数据
- 直接操作数据库层内部对象
- 直接访问页面私有状态
- 直接修改系统级安全设置
- 让业务逻辑散落在 Prompt 里

### 2.3 AI 与业务层的关系

AI 不是业务规则的替代品。它只能通过工具和用例层间接作用于数据。

正确关系是：

```text
AI -> Tool -> UseCase / Service -> Repository -> Data Source
```

而不是：

```text
AI -> DB / Page / Rule Engine internals
```

---

## 3. 总体结构

建议把 AI 平台分为 7 个子层：

```text
runtime  ->  会话循环、流式输出、调度、错误恢复
tool     ->  工具注册、参数校验、调用分发
bridge   ->  领域桥接，AI 与业务隔离
skill    ->  领域技能、意图提示、能力声明
model    ->  消息、配置、Provider、结果模型
log      ->  运行日志、审计、导出
ui       ->  对话页、任务页、日志页、状态展示
```

---

## 4. Runtime 层

### 4.1 职责

Runtime 层负责 AI 会话的完整执行循环：

1. 接收用户输入
2. 组装上下文
3. 发送给模型
4. 解析流式输出
5. 识别工具调用
6. 执行工具
7. 汇总结果
8. 决定下一轮循环或结束

### 4.2 关键能力

- SSE / 流式输出
- tool call 解析
- 多轮循环
- 超时控制
- 重试与降级
- token / 预算控制
- 会话持久化

### 4.3 运行策略

建议采用“有限循环”而不是无限循环：

- 每次任务限定最大轮数
- 每轮限定最大工具数
- 每个工具限定最大耗时
- 写操作必须显式确认

### 4.4 失败处理

- 模型超时：停止本轮，返回可理解错误
- 工具失败：输出局部结果并记录日志
- 流式中断：回退为非流式或续写提示
- 参数异常：进行容错修正后再调用

---

## 5. Tool 层

### 5.1 职责

Tool 层负责把“自然语言意图”变成“具体动作”。

它应该具备：

- 工具注册
- 参数校验
- 工具权限判断
- 工具调用
- 工具结果标准化
- 工具错误包装

### 5.2 工具分类

建议按领域分组：

#### 选书工具
- 搜索书籍
- 推荐书籍

#### 读书工具
- 读取章节
- 总结章节
- 回顾剧情

#### 懂书工具
- 分析人物
- 解释文本
- 分析主题

#### 书源工具
- 分析书源
- 查看规则
- 列表统计
- 测试书源
- 提供修复建议

#### 书架工具
- 列出书架
- 打开书籍
- 删除书籍
- 打开搜索
- 打开书架页面

#### 设置工具
- 获取设置
- 修改设置

### 5.3 工具约束

- 只暴露必要参数
- 参数必须做类型和范围检查
- 写操作工具必须进入确认态
- 工具结果必须是结构化结果，不是随意字符串拼接

---

## 6. Bridge 层

### 6.1 职责

Bridge 层是最重要的隔离层之一。它负责把 AI 请求翻译成业务层可执行的操作。

它的作用是：

- 把 AI 的意图转换成稳定的业务调用
- 屏蔽数据库、网络、规则引擎的内部细节
- 限制 AI 访问范围
- 统一写操作的授权流程

### 6.2 设计原则

- AI 不直接拿到 Repository 实例
- AI 只拿到 Bridge 暴露的能力
- Bridge 负责做二次确认前的最终检查
- Bridge 负责把结果转成 AI 可理解的上下文

---

## 7. Skill 层

### 7.1 职责

Skill 层定义“AI 在这个项目里应该擅长什么”。

它不是普通 Prompt，而是领域能力声明。

### 7.2 建议技能分类

- 选书技能
- 阅读技能
- 总结技能
- 分析技能
- 书源诊断技能
- 设置管理技能
- 安全写操作技能

### 7.3 技能的作用

- 帮助 AI 选择合适工具
- 帮助 AI 形成稳定任务策略
- 帮助 AI 在不同场景使用不同输出风格

---

## 8. Memory 层

### 8.1 职责

Memory 层记录用户长期偏好和任务上下文。

### 8.2 建议存储的内容

- 常用服务商
- 常用模型
- 语言偏好
- 阅读偏好
- 常用书架行为
- 常用工具路径
- 最近任务上下文

### 8.3 不建议长期保存的内容

- 敏感凭证明文
- 不必要的短期中间步骤
- 大量一次性噪声

### 8.4 记忆策略

建议采用分层记忆：

- 会话级记忆：只在当前会话有效
- 用户级记忆：跨会话稳定存在
- 临时任务记忆：完成后可清理

---

## 9. Workflow 层

### 9.1 为什么要有 Workflow

很多 AI 任务不是单轮问答，而是多步执行：

- 用户问“帮我找一本适合现在看的书”
- 系统要先理解偏好
- 再搜索
- 再筛选
- 再展示
- 可能还要加入书架

这类任务适合 Workflow。

### 9.2 建议的工作流类型

- 搜书工作流
- 读书总结工作流
- 书源诊断工作流
- 设置修改工作流
- 受控写操作工作流

### 9.3 Workflow 设计原则

- 每步都有输入输出
- 每步都可中断
- 每步都可回放
- 写操作前必须确认

---

## 10. Provider 层

### 10.1 职责

Provider 层负责对接不同 AI 服务商：

- 统一接口
- 统一错误处理
- 统一流式格式
- 统一参数兼容

### 10.2 设计目标

- 支持 OpenAI 兼容接口
- 支持不同厂商的参数差异
- 支持流式与非流式切换
- 支持本地模型

### 10.3 Provider 设计原则

- Provider 不应参与业务规则
- Provider 只做通信和格式适配
- 业务逻辑不依赖某一家厂商

---

## 11. 写操作确认机制

写操作确认是 AI 平台的安全核心。

### 11.1 典型写操作

- 删除书籍
- 修改书源启用状态
- 修改设置
- 清理数据
- 同步覆盖

### 11.2 确认机制要求

- AI 只能生成提案
- 提案必须展示给用户
- 用户确认后才能执行
- 超时自动失效
- 拒绝后不可重复写入同一动作

### 11.3 安全目的

- 防止误操作
- 防止模型幻觉造成破坏性修改
- 防止自动化任务越权

---

## 12. 可观测性

### 12.1 必须记录的内容

- 用户输入
- 模型请求
- 模型响应
- 工具调用
- 工具结果
- 错误堆栈
- 确认状态
- 任务耗时

### 12.2 日志分级

- 用户可见日志
- 开发调试日志
- 审计日志

### 12.3 日志目标

- 出问题可定位
- 操作可回放
- 错误可解释
- AI 决策可追踪

---

## 13. 与 UI 的关系

UI 不应该“伪装成 AI 平台”。UI 应该只是 AI 平台的展示层。

建议界面分为：

- 对话区
- 任务区
- 工具结果区
- 日志区

这样用户能区分：

- AI 正在说话
- AI 正在执行
- AI 需要确认
- AI 执行失败了

---

## 14. 与现有代码的对应关系

当前仓库已经具备的 AI 分区可以继续沿用，并逐步规范化：

- `runtime`：会话循环、流式输出、KeyStore、会话持久化
- `tool`：工具注册、调用解析
- `bridge`：领域桥接
- `skill`：领域技能
- `model`：消息与配置模型
- `log`：日志系统
- `ui`：对话页、日志页、背景

这说明当前项目已经有平台雏形，下一步不是“从零开始”，而是“把雏形收敛成正式架构”。

---

## 15. 未来兼容方向

### 15.1 MCP / 工具协议兼容

未来如果扩展到更多外部工具体系，建议工具层保留协议适配能力，而不是绑定单一标准。

### 15.2 多模型路由

未来可按任务类型路由模型：

- 快速问答模型
- 长上下文模型
- 工具调用模型
- 本地离线模型

### 15.3 Agent 市场化

未来可以开放：

- 预设 Agent
- 预设 Prompt
- 预设工具集
- 预设 Workflow

---

## 16. AI 平台结论

legado 的 AI 平台最重要的不是“聊天更像人”，而是：

1. 能理解任务
2. 能调用工具
3. 能受控写入
4. 能审计回放
5. 能和阅读核心协作

这才是 AI 原生阅读平台应有的方向。
