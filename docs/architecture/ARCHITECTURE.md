# legado 总体架构设计

> 版本：Draft 1
>
> 目标：为 legado 建立统一的架构蓝图，作为后续 AI 平台、UI 重构、性能优化、安全加固、插件系统与长期演进的共同依据。

---

## 1. 项目定位

legado 是一个以“阅读体验”为核心的 Android 应用，同时逐步演进为一个具备 AI Agent 能力的阅读平台。它不仅负责展示书籍内容，还要完成以下任务：

- 管理书架与阅读进度
- 连接本地书籍、网络书源与 RSS 内容
- 提供章节解析、搜索与朗读能力
- 允许 AI 参与搜书、读书、总结、诊断、修复建议等工作
- 在保证安全与稳定的前提下，支持可扩展的工具体系与未来生态

因此，legado 的架构不应只被理解为“一个 Android 阅读器”，而应被理解为：

> **阅读核心 + 书源引擎 + AI Agent 平台 + 可扩展 UI 与工具系统**

---

## 2. 架构目标

### 2.1 稳定

核心阅读能力必须长期稳定运行，不能因为 AI、插件、主题或新功能引入而破坏原有体验。

### 2.2 可维护

业务逻辑、数据逻辑、UI 逻辑应尽可能解耦，便于定位问题、修改功能、替换实现。

### 2.3 可扩展

未来新增 AI 工具、阅读能力、主题、插件、同步能力时，不应依赖大规模改写。

### 2.4 可观测

系统需要具备足够清晰的日志、状态、错误提示与调试手段，以便排查书源、AI 调用和页面交互问题。

### 2.5 可演进

架构必须允许渐进式改造，而不是一次性推倒重来。老功能与新功能应可以长期共存。

---

## 3. 架构原则

### 3.1 单向数据流

UI 只负责展示与事件收集，状态由 ViewModel 或等价状态层统一管理。

### 3.2 依赖反转

上层依赖抽象，不直接依赖底层实现。UI 不应直接操作数据库、网络请求或脚本引擎。

### 3.3 模块自治

每个模块只负责自己的业务边界：阅读、书源、AI、设置、日志、下载、同步等。

### 3.4 写操作显式化

涉及用户书架、设置、书源、数据修改的行为必须经过明确确认或显式调用，避免误操作。

### 3.5 失败可回退

任何网络失败、解析失败、模型失败、工具失败都应有降级路径。

## 4. 逻辑分层

建议将项目逻辑划分为以下层：

```text
Presentation / UI
   ↓
State / ViewModel
   ↓
Domain / UseCase
   ↓
Repository / Service
   ↓
Data Source / Engine
```

### 4.1 Presentation / UI

职责：

- 展示信息
- 收集用户输入
- 触发页面事件
- 渲染状态变化

不应包含：

- 复杂规则执行
- 数据库存取细节
- 网络重试策略
- AI 工具编排逻辑

### 4.2 State / ViewModel

职责：

- 聚合页面状态
- 管理加载、成功、失败、空态
- 调用业务用例
- 转换领域结果为 UI 可渲染状态

### 4.3 Domain / UseCase

职责：

- 表达业务规则
- 编排多个 Repository / Service
- 管理关键流程，例如搜索、解析、总结、诊断、写操作确认

### 4.4 Repository / Service

职责：

- 对外提供统一的数据访问接口
- 屏蔽本地数据库、远程接口、规则引擎、缓存差异
- 作为模块边界

### 4.5 Data Source / Engine

职责：

- 数据库访问
- 网络请求
- 规则解析
- AI Provider 调用
- 缓存读写
- 文件系统访问

---

## 5. 核心模块划分

### 5.1 阅读模块

阅读模块负责：

- 章节展示
- 章节切换
- 阅读进度保存
- 翻页与滚动模式
- 字体、间距、背景、亮度等阅读设置
- 朗读与章节导出

关键点：阅读模块必须保持高性能、低抖动、低延迟。

### 5.2 书源模块

书源模块负责：

- 搜索
- 书源测试
- 内容抓取
- 章节解析
- 规则调试
- 书源状态管理

关键点：书源模块是系统兼容性最复杂的部分，必须具备强容错和强隔离能力。

### 5.3 AI 平台模块

AI 平台模块负责：

- 会话管理
- Prompt 组装
- 工具调用
- 流式输出
- 写操作确认
- 运行日志
- 记忆管理
- Provider 适配

关键点：AI 不应直接绕过领域层，不应直接操作底层数据库或随意改写用户数据。

### 5.4 书架模块

书架模块负责：

- 书籍收纳
- 分类与排序
- 最近阅读
- 更新提醒
- 批量管理
- 置顶与收藏

### 5.5 下载与导入模块

负责：

- 本地文件导入
- 封面与章节资源下载
- 任务队列管理
- 下载状态展示

### 5.6 设置与个性化模块

负责：

- 阅读配置
- 主题配置
- AI 配置
- 服务商配置
- 备份恢复

### 5.7 日志与调试模块

负责：

- 操作日志
- AI 调用日志
- 工具调用日志
- 书源异常日志
- 导出与分享

---

## 6. 推荐的模块边界

### 6.1 AI 与阅读分离

AI 可以“看见”阅读数据，但不应直接依赖阅读页面细节。

推荐方式：

- 阅读模块输出标准化上下文
- AI 平台读取上下文并生成结果
- AI 的结果再由 UI 层展示或交回业务层处理

### 6.2 AI 与数据库分离

AI 不应直接拿数据库对象做读写。

推荐方式：

- AI 通过工具接口访问书架、书源、设置、日志等能力
- 工具层负责校验权限与参数
- 工具层再调用业务层或 Repository

### 6.3 UI 与规则引擎分离

UI 不应拼接规则执行逻辑。

推荐方式：

- UI 发起请求
- ViewModel 调用 UseCase
- UseCase 调用 Rule Engine
- Rule Engine 输出结构化结果

## 7. 数据流设计

### 7.1 常规页面数据流

```text
用户操作
  ↓
UI 事件
  ↓
ViewModel
  ↓
UseCase
  ↓
Repository
  ↓
Data Source
  ↓
结果回传
  ↓
UI 状态更新
```

### 7.2 AI 任务数据流

```text
用户输入
  ↓
AI 会话上下文
  ↓
Prompt / Tool Planning
  ↓
Tool Call / Text Protocol
  ↓
工具执行
  ↓
结果聚合
  ↓
流式输出 / 确认 / 落库
```

### 7.3 书源搜索数据流

```text
搜索请求
  ↓
搜索策略
  ↓
多个书源并发执行
  ↓
结果去重与排序
  ↓
过滤与评分
  ↓
UI 展示
```

## 8. 状态模型

建议将页面状态统一为以下类型：

- Loading
- Success
- Empty
- Error
- ConfirmRequired
- Streaming
- PartialResult

这样可以让 UI、AI、书源、下载等模块的状态表现保持一致。

## 9. 目录建议

推荐逐步形成以下结构：

```text
app/src/main/java/io/legado/app/
├── ai/
├── data/
├── domain/
├── repository/
├── rule/
├── reader/
├── bookshelf/
├── setting/
├── download/
├── ui/
├── util/
└── log/
```

### 9.1 说明

- `ai/`：AI 平台与工具调用
- `data/`：底层数据源与持久化
- `domain/`：领域业务用例
- `repository/`：抽象数据访问
- `rule/`：书源与解析规则
- `reader/`：阅读相关核心逻辑
- `bookshelf/`：书架管理
- `setting/`：设置与配置
- `download/`：下载与导入
- `ui/`：界面层与页面状态
- `util/`：通用工具
- `log/`：日志与调试

## 10. 技术演进路线

### 第一阶段：稳定化

- 收敛旧式耦合代码
- 梳理核心边界
- 统一错误处理和日志
- 建立基础文档体系

### 第二阶段：现代化

- 统一状态管理
- 清理过时的 UI 与数据写法
- 改善异步与缓存
- 逐步引入更清晰的分层结构

### 第三阶段：平台化

- AI Agent 工具化
- 书源诊断平台化
- 插件与主题系统化
- 形成可扩展生态

### 第四阶段：生态化

- 规则分享
- Prompt 分享
- AI 预设分享
- 主题与插件市场

---

## 11. 风险与约束

### 11.1 风险

- 大规模重构可能导致阅读主链路不稳定
- AI 能力扩张后可能引入复杂权限问题
- 书源规则兼容性差异大，容易出现回归

### 11.2 约束

- 不能破坏原有核心阅读体验
- 不能让 AI 绕过确认机制
- 不能让新架构过度复杂化
- 必须支持渐进迁移

---

## 12. 本项目的架构结论

legado 的最佳路线不是“推倒重做”，而是：

1. **稳定核心阅读能力**
2. **把 AI 做成平台能力**
3. **把 UI 做成统一体验**
4. **把模块拆成可维护边界**
5. **把文档变成真正的开发依据**
