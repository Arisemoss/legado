# legado 路线图

> 版本：Draft 2
>
> 目标：在保持原有阅读能力稳定的前提下，把 legado 逐步演进成一个 **Compose-first、模块化、状态驱动、AI 工具化** 的阅读平台。
>
> 这份路线图不是功能清单，而是项目未来 12~24 个月最适合的前进方向。

---

## 1. 方向判断

legado 现在最重要的不是继续堆功能，而是把“能用”升级成“可持续演进”。

结合当前项目现状，最值得优先推进的方向有四个：

1. **UI 现代化**：新页面优先 Compose，旧页面渐进迁移，避免一次性重写。
2. **架构模块化**：把阅读、书源、AI、设置、日志、下载拆成边界清晰的模块。
3. **状态驱动化**：统一 UI 状态、页面事件和业务结果流转方式。
4. **AI 平台化**：让 AI 变成可执行任务的 Agent，而不是只负责聊天。

这四个方向与 Android 官方当前的推荐方向一致：Compose 是推荐的现代 UI 工具；Compose 与 Views 支持渐进式共存；ViewModel 应暴露单一 UI state；UDF 和 `StateFlow` 更适合驱动 UI；模块化能提升可维护性、测试性和构建效率；后台持久任务应使用 WorkManager。 

---

## 2. 总体战略

### 2.1 第一优先级：稳定主链路

主链路包括：

- 打开书架
- 搜索书籍
- 打开章节
- 阅读翻页
- 书源解析
- AI 基础对话
- 工具调用

这些能力不能因为重构而退化。

### 2.2 第二优先级：重建工程边界

把现在偏“单体式”的组织方式，改造成可以继续增长的模块化结构。

### 2.3 第三优先级：升级体验

UI 的目标不是更花哨，而是更统一、更轻快、更少找按钮、更少断层。

### 2.4 第四优先级：形成平台

AI、主题、插件、Prompt、书源、规则、同步都应该朝平台化演进。

---

## 3. 推荐技术路线

### 3.1 UI：Compose-first，保留 Views 过渡层

推荐方案不是推倒重做，而是 **混合迁移**：

- 新页面优先用 Compose
- 核心旧页面逐步拆成可替换的 Compose 组件
- 过渡期通过 `ComposeView` / `AndroidView` 共存
- 迁移节奏按页面价值和改造成本排序

这样做的原因是：

- Compose 是 Android 当前推荐的现代 UI 工具
- 官方明确支持 Compose 与 Views 渐进式互操作
- 新的 Android Studio UI 工具也更偏向 Compose

### 3.2 架构：ViewModel + UDF + StateFlow

推荐统一成：

```text
UI / Screen
  ↓
ViewModel
  ↓
UseCase
  ↓
Repository
  ↓
Data Source / Engine
```

原则：

- UI 只发事件，不直接改业务状态
- ViewModel 只暴露一个或少数几个 `uiState`
- 状态使用不可变数据结构
- 复杂业务逻辑下沉到 UseCase
- 数据访问统一进 Repository

### 3.3 后台任务：WorkManager

建议把以下内容尽量纳入 WorkManager：

- 书源更新
- 封面/章节下载
- 离线同步
- 日志导出
- 需要可靠执行的异步修复任务

原因：WorkManager 是 Android 推荐的持久化后台任务库，适合带约束条件的可靠执行。

### 3.4 模块化：先“按边界拆”，再“按特性拆”

模块化不建议一开始就过度细分。更合理的顺序是：

1. 先把数据层、领域层、UI 层拆开
2. 再把大功能拆为 feature module
3. 最后再考虑 api/impl 级别的细颗粒拆分

Android 官方对模块化的建议强调：模块化能改善可维护性、封装性、测试性和构建性能，但颗粒度过细也会带来额外复杂度，因此要根据项目规模逐步推进。

### 3.5 AI：工具优先，Agent 化，带可审计执行链

AI 平台不应只做自然语言问答，而应围绕“可执行任务”构建：

- 搜书
- 选书
- 读书
- 总结
- 分析
- 诊断
- 提案
- 受控写操作

AI 调用链要具备：

- 规划
- 工具执行
- 结果回填
- 日志审计
- 失败回退

如果参考当前主流平台的产品方向，工具调用、流式输出、Agent 工作流、编排能力正在成为平台型 AI 的核心能力，而不是附属功能。

## 4. 分阶段路线图

### Phase 1：稳定与整理

目标：先把地基打牢。

工作项：

- 整理目录结构
- 统一命名规范
- 建立架构文档中心
- 把核心页面和核心业务边界梳理清楚
- 统一日志、错误、加载态
- 清理最容易出问题的耦合点

验收标准：

- 核心阅读链路稳定
- AI 基础能力稳定
- 书源错误可定位
- 新文档能指导开发，不是只做展示

---

### Phase 2：现代化改造

目标：让项目具备更现代的 Android 工程形态。

工作项：

- 新页面优先 Compose
- 旧页面逐步迁移
- 建立统一 UI State
- 引入或强化 `StateFlow`
- 推动 ViewModel 标准化
- 把重任务迁到 WorkManager
- 收敛页面内业务逻辑

验收标准：

- 页面状态表达统一
- 页面之间的数据流更清晰
- 重任务不会堵主线程
- UI 改动不再牵一发而动全身

---

### Phase 3：模块化重组

目标：让项目从“单体工程”走向“可持续扩展的多模块工程”。

建议模块：

- `:app` 主壳
- `:core:model`
- `:core:ui`
- `:core:data`
- `:core:common`
- `:feature:bookshelf`
- `:feature:reader`
- `:feature:search`
- `:feature:ai`
- `:feature:settings`
- `:feature:log`
- `:feature:download`

这不是最终答案，而是一个适合逐步拆分的方向。

验收标准：

- 模块边界明确
- feature 可独立演进
- 内部实现不被外部随意依赖
- 构建时间和测试可控

---

### Phase 4：AI 平台升级

目标：让 AI 从“会说话”升级成“会做事”。

工作项：

- 工具注册体系再整理
- 写操作确认流程标准化
- 增加任务状态追踪
- 增加记忆层
- 增加更细粒度的技能层
- 增加 Agent 工作流模板
- 增加工具链审计与回放

验收标准：

- AI 能稳定完成任务
- 工具调用链可追踪
- 写操作不会绕过确认
- 错误时能给出可理解的降级结果

---

### Phase 5：生态化

目标：把项目变成平台。

工作项：

- 主题系统
- Prompt 预设
- Agent 预设
- 插件接口
- 书源/规则分享机制
- AI 工具扩展点
- 同步与备份能力

验收标准：

- 新能力可扩展而不改主干
- 社区贡献可以模块化接入
- 不同用户可以只启用自己需要的功能

## 5. UI 路线图

### 5.1 首页

首页从“功能堆叠”改成“入口分层”：

- 顶部：搜索、AI、设置
- 中部：继续阅读、最近更新、AI 提示卡
- 底部：书架、发现、AI、下载、我的

目标：减少跳转，减少认知负担。

### 5.2 书架页

建议保留多种展示模式：

- 列表
- 网格
- 大封面
- 最近阅读

并提供：

- 置顶
- 批量管理
- 空状态引导
- 更新提醒

### 5.3 阅读页

阅读页是核心体验，优先级最高。

重点：

- 统一字体、行高、边距、段落节奏
- 夜间/日间主题稳定
- 顶栏和底栏自动隐藏
- 翻页动画与滚动反馈更自然
- 阅读设置入口更快更直观

### 5.4 AI 页

AI 页建议分成三层：

- 聊天区
- 工具结果区
- 任务状态区

这样用户能区分：模型在说话、模型在执行、模型在等待确认。

## 7. 不建议现在做的事

- 一次性全量重写成 Compose
- 一次性拆成过多 Gradle module
- 一次性重做所有书源机制
- 在没有统一状态规范前继续堆新页面
- 在没有工具审计之前继续放大 AI 写操作能力

---

## 8. 结论

legado 最好的前进方向不是“更大”，而是“更稳、更清晰、更可扩展”。

路线应当是：

1. **稳住核心阅读能力**
2. **用 Compose 和状态驱动重建 UI 体验**
3. **用模块化重建工程边界**
4. **用 WorkManager 收敛可靠后台任务**
5. **用 Agent 化把 AI 变成平台能力**
6. **用插件和预设把项目变成生态**
